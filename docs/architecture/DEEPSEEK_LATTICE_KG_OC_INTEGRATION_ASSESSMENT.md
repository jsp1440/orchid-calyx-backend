## 1. Executive Summary

DeepSeek-Lattice-KG describes a recognizable graph-augmented QA pattern: interpret a question, retrieve graph context, then generate an answer. That pattern is relevant, but the checked-in repository does not contain an executable question-to-Cypher/retrieval/generation pipeline, a fine-tuning pipeline, a benchmark harness, or a scientific disagreement model. Its README's scale, accuracy, and traceability statements are claims, not independently reproducible evidence in the repository snapshot.

Orchid Continuum already has more suitable primitives in this backend: canonical taxonomy/ontology resolution; literature claims, evidence, source spans, review and reconciliation; an existing PostgreSQL graph interface; qualified assertion publication with provenance links; hybrid evidence retrieval with citation/anchor metadata; and a versioned, conflict-aware Reasoning Ledger. These primitives are distributed across modules. The open integration issue #181 itself describes remaining work in wiring them into one verified end-to-end path, so this audit does **not** claim that the complete scientific-answer pipeline is already certified.

**Recommendation:** Do not import the reference implementation or add Neo4j. Adapt only the high-level idea of bounded graph context plus evidence retrieval into an isolated, read-only adapter using OC's existing interfaces. Prioritize a frozen, provenance-first scientific reasoning benchmark before comparing model quality or considering fine-tuning. Preserve each incompatible assertion as a separate, source-backed record; never turn disagreement into one canonical edge.

## 3. DeepSeek-Lattice-KG Architecture

The public tree at the pinned revision contains eight files: `README.md`, `LICENSE`, `neo4j_json_importer.py`, `Knowledge Graph/kg_extraction/{__init__.py,config.py,main.py}`, and `Knowledge Graph/kg_extraction/processors/{__init__.py,extraction.py}`. The two `__init__.py` files contain no substantive pipeline. The checked tree contains no tests, benchmark data/runner, requirements/lock file, fine-tuning scripts, model weights, graph-query service, or question-answering service.

* **README-described design:** extraction from literature; a 14B domain-adapted model; Neo4j graph; question understanding → Cypher retrieval → generation; iterative graph updates; claims of 50,000 papers, 658,623 entities, 622,344 relations, 94.2% on 2,100 questions, and 93% on emerging topics. These are README claims only in this repository snapshot.
* **Implemented extraction:** `KnowledgeGraphExtractor.extract_kg` prompts DashScope to emit `entity|relationship|entity` strings from one text input; parses lines; writes Markdown triples. `doc_id` appears in the output filename, not in a structured source/evidence record. `_validate_and_count` only sets a count and returns `True`.
* **Implemented loader:** `Neo4jImporter` reads JSON records with `start_node` and `end_node`, sanitizes names/type strings, then `MERGE`s `Entity{name}` nodes and a typed edge. It does not create assertion/evidence/source/revision nodes, source spans, taxonomic concepts, confidence, or support/contradiction links.
* **Not implemented in the inspected tree:** a defined ontology, independent entity/relation extractors, question parser, NL-to-Cypher generator, subgraph retrieval service, answer-generation integration, model/fine-tune pipeline, train/Q&A set construction, benchmark runner, or reliability evaluation. README descriptions do not substitute for those absent artifacts.
* **Incremental-update qualification:** README describes continuous updates, but the available code is a local text-folder extraction script plus a JSON importer. No scheduler, source-version ledger, review queue, deletion/retraction handling, retry checkpoint or end-to-end idempotent update protocol is present in the tree.

Reference sources: [pinned README](https://github.com/YanChen32/DeepSeek-Lattice-KG/blob/d2babd18c86172e983c2a478d9c784bbaf55c31e/README.md), [extractor](https://github.com/YanChen32/DeepSeek-Lattice-KG/blob/d2babd18c86172e983c2a478d9c784bbaf55c31e/Knowledge%20Graph/kg_extraction/processors/extraction.py), [importer](https://github.com/YanChen32/DeepSeek-Lattice-KG/blob/d2babd18c86172e983c2a478d9c784bbaf55c31e/neo4j_json_importer.py), [configuration](https://github.com/YanChen32/DeepSeek-Lattice-KG/blob/d2babd18c86172e983c2a478d9c784bbaf55c31e/Knowledge%20Graph/kg_extraction/config.py), [source tree](https://github.com/YanChen32/DeepSeek-Lattice-KG/tree/d2babd18c86172e983c2a478d9c784bbaf55c31e).

## 7. KG / Graph Retrieval Assessment

**What is materially different in the reference?** The README presents graph retrieval followed by answer generation as a coherent workflow. The checked-in source does not implement the described question parser, generated Cypher, retrieval, or generation, so it offers no verifiable capability over OC's existing `PostgresGraphRepository`, `/brain` graph routes, `RetrievalEngine`, or governed provider context.

**What the current OC stack already supplies:** PostgreSQL graph nodes/edges; a graph repository boundary; bounded relationship reads and deterministic reasoning maps; lexical plus vector document retrieval with filters, display policy, source anchors and citation metadata; plus controlled graph change sets and publication versions. A bounded read-only join of these records can be implemented using existing PostgreSQL and repository interfaces. This should use typed query plans and fixed depth/result limits, not model-produced Cypher.

**Neo4j decision: DO NOT USE.** The reference importer proves a Neo4j driver integration, not a requirement OC cannot satisfy. Neo4j could provide a graph-native Cypher environment, graph visualization/tooling and potentially better latency for some deep/high-degree traversals. The inspected evidence includes no representative OC traversal workload, benchmark, latency target, or feature unavailable in PostgreSQL that justifies another database. No performance advantage can responsibly be quantified from these repositories. The objectively identifiable delta is operational: another database service/runtime, credentials and connection path, deployment configuration, schema/identity synchronization, monitoring, backup/restore, access controls and failure mode. That is not justified before a same-data, same-query benchmark shows a material unmet requirement.

If a later measurement demonstrates a gap, compare candidate PostgreSQL query plans/indexes and bounded recursive SQL against Neo4j on a frozen OC workload first. Any experiment must remain non-production, read-only to canonical state, and avoid a second source of truth.

## 8. Scientific Disagreement and Provenance Assessment

**DeepSeek-Lattice-KG does not adequately model scientific disagreement in the inspected implementation.** Its extraction output is a three-part string. `Neo4jImporter._create_relationship` identifies an edge by normalized endpoint names and relationship type, then merges it. There is no first-class assertion with source, author, publication/date, evidence type, taxonomic concept, confidence, supporting evidence or counterevidence. Distinct reports with contrary values can become competing/unattributed edges or collide through name normalization. The README's traceability claim is not supported by source-span or provenance fields in these files.

OC has appropriate, though distributed, structures:

* literature `Claim` / `Evidence` / `NormalizedEvidenceRecord` retain polarity, evidence IDs, source excerpts, review state, confidence, reconciliation group and provenance; `ReconciliationRelation` distinguishes support from potential contradiction;
* `DocumentIntelligenceBindingResolver` verifies the source hash and unique document/revision/run/anchor and blocks ambiguous bindings;
* `AssertionGraphMapper` creates a separate `qualified_assertion` node keyed by assertion identity/version and material context, then records supporting and conflicting interpretation IDs;
* `oc_knowledge_publication.graph_provenance_links` retain assertion/version, interpretation, evidence packet, source revision and provenance records;
* Reasoning Ledger entries retain separate support, counterevidence, conflict, uncertainty, provenance and immutable conflict dispositions.

**Important boundary:** `PublicationAuthority.evaluate` can fail closed when unresolved conflicting interpretation IDs violate publication policy. That is a governance block, not permission to delete or reconcile away the conflicting evidence. Preserve all incompatible assertions and provenance in candidate/evidence/reasoning records; publication may remain blocked pending review. A later reviewed resolution should record rationale, actor and time without rewriting what each source asserted.

For each assertion OC must keep its own subject and predicate/object/value plus its source/authorship/publication/date, evidence type and locator, applicable taxon concept and version, method/confidence, supports, contradicts, temporal/geographic/experimental scope and immutable provenance. Consensus, if eventually curated, must be a distinct reviewed synthesis object linked to—not substituted for—the source assertions. Missing/ambiguous taxon binding or evidence must remain explicit.

## 10. OC Scientific Reasoning Benchmark Proposal

Create a versioned, expert-reviewed regression set with one record per case: question and task type; canonical taxa/concepts and version; source assertions with revision/hash/anchor; expected answer facets; allowed uncertainty/abstention; contradiction links; gold multi-hop path; evaluator version; and dataset/license provenance. Keep a held-out split grouped by source publication and taxonomic concept to prevent leakage. Record adjudicator disagreements instead of forcing unsupported single answers.

**Required case families:** taxonomy and historical-name resolution; nomenclature/synonymy; distribution and sensitive locality; ecology and habitat; morphology/trait measurements and units; pollinator interaction; mycorrhiza; phenology; conservation; cultivation; literature interpretation; conflicting evidence; taxonomic disagreement; source/provenance validation; multi-hop reasoning; and uncertainty/missing evidence.

**Cross-module challenge cases** should include, at minimum:

1. Resolve a historical taxon name, retrieve a cited occurrence record, preserve its date/geographic uncertainty, and avoid treating a synonym as a second species.
2. Connect a floral morphology observation to a pollination claim, its literature evidence, and a contradictory source; do not infer causal pollinator dependence from correlation.
3. Reconcile a fungal association report with a second report using distinct taxon concepts and methods; identify whether apparent conflict is biological, taxonomic or methodological.
4. Combine phenology and distribution evidence for a conservation window while respecting source dates, spatial uncertainty and sensitive-locality display policy.
5. Compare trait measurements across methods, units and sample sizes, preserve incompatible results, and abstain where normalization is not defensible.
6. Answer a cultivation question by separating source-reported practice, experimental result and recommendation, then trace each factual clause to literature.
7. Ask a question with a missing evidence edge; the expected result states the gap rather than completing a plausible multi-hop chain.
8. Present an unresolved nomenclatural/taxonomic disagreement; expected result returns competing assertions, concept versions and review state rather than selecting a winner.

**Regression metrics:** per-domain exact concept binding and misbinding; fact/claim precision and recall; citation/revision/anchor resolution; evidence support and contradiction recall; multi-hop path exactness; uncertainty/abstention precision and recall; confidence calibration (Brier score and calibration error); policy/privacy violations; and latency/cost where model-backed. Report domain-wise values and confidence intervals, not only a pooled accuracy.

**Release gate proposal:** 100% of emitted citations must resolve to the expected versioned source and permitted anchor; zero fabricated citation IDs; zero canonical-taxon misbindings on adjudicated ambiguity/historical-name cases; all designated contradictory assertions remain separately represented and the answer identifies unresolved disagreement; zero unsupported causal claims; required abstention on benchmark cases with no supporting evidence; and no statistically meaningful regression beyond pre-registered per-domain tolerances. Set retrieval/answer quality floors from a measured baseline before comparing models. A release is not “better” on demonstrations alone: the exact frozen suite, evaluator, evidence snapshot and model/provider revision must be recorded.

## 11. Infrastructure Impact

No infrastructure change is recommended. The proposed experiment can use in-memory/test doubles or a disposable PostgreSQL instance loaded with existing OC fixtures, and can call existing repository/retrieval interfaces in read-only mode. It requires no production `DATABASE_URL`, service mutation, migration, model provider, Neo4j, Render/Neon change or fine-tuning.

Adding Neo4j now would introduce at least one new database runtime/service and independent credentials, network policy, deployment, schema, backup/restore, monitoring and reconciliation surfaces. The reference repository does not establish an OC-sized performance requirement or measured win to offset them. Data transfer, synchronization or a second canonical graph would additionally risk stale and conflicting state.

## 12. Integration Risks

| Risk | Why it matters | Mitigation |
|---|---|---|
| Flat triples erase disagreement and assertion context | Conflicting literature can collapse into a single edge or be mislabeled as fact | Keep evidence-backed assertions separate; preserve polarity, scope and source identity. |
| Generated Cypher crosses the data/query boundary | Can execute unbounded, incorrect or unsafe traversal and may expose data | Use a typed query plan mapped to allowlisted parameterized repository operations and hard limits. |
| Name-only identity | Synonyms, historical names and distinct taxonomic concepts collide | Require canonical concept ID + taxonomy release; preserve unresolved/ambiguous candidates. |
| LLM extraction promoted as verified evidence | Model-produced relations are hypotheses, not source evidence | Keep extraction candidates review-required; bind exact source spans and hash before acceptance. |
| README metrics treated as reproducible proof | No benchmark artifacts or evaluation script exist in the inspected tree | Reproduce from a fixed OC dataset/evaluator; record exact model, retrieval snapshot and split. |
| Rights assumptions | MIT software license does not grant paper, corpus, checkpoint or provider rights | License-check software, dataset, checkpoint, benchmark and dependencies independently. |
| Unreviewed incremental mutation | Retractions, changed evidence, and duplicates can corrupt durable scientific state | Use existing versioned publication lifecycle, idempotency, review and audit mechanisms. |
| Duplicate system/authority | A Neo4j graph or parallel orchestrator can diverge from OC's canonical components | Keep PostgreSQL/KG and durable Calyx substrate authoritative; use adapters only. |
| Overstated operational maturity | Code/tests are not proof of a live or certified service | Keep claims at source-evidence level; require exact environment/run evidence separately. |

## 13. Recommended Architecture

Use the existing flow and preserve clear record types:

`question → typed intent/concept request → canonical taxon binding (or explicit ambiguity) → bounded PostgreSQL KG context + evidence retrieval → assertion/evidence packet → claim-by-claim synthesis → support/counterevidence/conflict and uncertainty review → source-backed answer`

The query adapter should be an isolated, read-only module with a versioned input/output contract and dependency-injected graph/evidence interfaces. It must not own a queue, model, new graph store, canonical taxon resolver, source registry, or publication process. Each retrieved graph fact remains a qualified assertion with graph version and provenance; each retrieved literature item retains revision and source anchor. Any answer-level synthesis must identify supported, contradicted, inferred and unavailable facets separately. Existing Reasoning Ledger and human publication gates remain authoritative. No generated Cypher or automatic scientific publication.
